## What `WORKFLOW.md` Becomes

`SymphonyElixir.Workflow` loads `WORKFLOW.md` as a plain text file with optional YAML front matter and a prompt body. The loader returns a map-shaped config plus `prompt` and `prompt_template`, both derived from the text after the closing `---` fence, trimmed for whitespace. If the file is missing, `Workflow.load/1` returns `{:error, {:missing_workflow_file, path, reason}}`; if the front matter is not a map, it returns `{:error, :workflow_front_matter_not_a_map}`. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/workflow.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/workflow.ex) and [`/Users/lihui/Documents/GitHub/symphony/elixir/test/symphony_elixir/core_test.exs`](/Users/lihui/Documents/GitHub/symphony/elixir/test/symphony_elixir/core_test.exs).

`WorkflowStore` wraps that loader with last-known-good caching. It reloads on demand and on a 1s poll, but if reload fails it keeps the previous workflow in memory and logs the failure. That matters because Go parity needs the same “bad reload does not brick the runtime” behavior. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/workflow_store.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/workflow_store.ex).

## External Config Shape

The runtime config is normalized into `SymphonyElixir.Config.Schema`, which is an embedded schema with these top-level groups: `tracker`, `polling`, `workspace`, `worker`, `agent`, `codex`, `hooks`, `observability`, and `server`. Defaults are baked into the schema, not scattered in callers. Important defaults include `tracker.endpoint = https://api.linear.app/graphql`, `tracker.active_states = ["Todo", "In Progress"]`, `tracker.terminal_states = ["Closed", "Cancelled", "Canceled", "Duplicate", "Done"]`, `polling.interval_ms = 30000`, `workspace.root = $TMPDIR/symphony_workspaces`, `agent.max_concurrent_agents = 10`, `agent.max_turns = 20`, `codex.command = "codex app-server"`, `codex.thread_sandbox = "workspace-write"`, `observability.dashboard_enabled = true`, and `server.host = "127.0.0.1"`. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex) and [`/Users/lihui/Documents/GitHub/symphony/elixir/test/support/test_support.exs`](/Users/lihui/Documents/GitHub/symphony/elixir/test/support/test_support.exs).

## Normalization and Validation Steps

`Config.Schema.parse/1` first normalizes all map keys to strings, drops `nil` values, casts into the embedded schema, then runs validation. After that it applies a second pass in `finalize_settings/1` to resolve secrets, canonicalize paths, and normalize nested maps. Validation is mostly shape-based, but `Config.validate!/0` adds semantic checks: tracker kind must be present, only `"linear"` and `"memory"` are accepted, and Linear requires both API token and project slug. `validate_state_limits/2` also enforces that per-state agent limits are positive integers and that state names are not blank. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex) and [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config.ex).

## Env Fallbacks and Secret Handling

The Elixir implementation supports runtime fallbacks from env vars in two places. `tracker.api_key` and `tracker.assignee` can be omitted in `WORKFLOW.md` and will resolve from `LINEAR_API_KEY` and `LINEAR_ASSIGNEE`. Those same fields also accept a literal env reference token like `$LINEAR_API_KEY`; missing or empty env values collapse to `nil` for secrets. `workspace.root` has the same token-style support, but a missing env value falls back to the default workspace root instead of `nil`. This is all centralized in `finalize_settings/1`, `resolve_secret_setting/2`, and `resolve_path_value/2`. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config/schema.ex).

## Linear-Specific Leakage

This config layer is not provider-neutral. It still encodes Linear terminology and expectations in several places: the default prompt says “Linear issue”, the validation path special-cases `tracker.kind == "linear"`, the secret env vars are named `LINEAR_*`, and the prompt-building fallback in `SymphonyElixir.Config.workflow_prompt/0` returns the Linear-specific template when the file prompt is blank. The tracker adapter selection also keys off `Config.settings!().tracker.kind`. See [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/config.ex), [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/prompt_builder.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/prompt_builder.ex), and [`/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/tracker.ex`](/Users/lihui/Documents/GitHub/symphony/elixir/lib/symphony_elixir/tracker.ex).

## Go Parity Implications

For Go, the safe parity target is not “copy the Elixir schema literally” but “preserve the same observable contract.” The contract to keep is: front matter loads into a typed runtime config, defaults are stable, bad reloads preserve the last good config, env fallbacks work the same way, and the current Linear assumptions stay visible only where compatibility requires them. The main divergence opportunity is to move the provider-neutral part into a cleaner internal model while keeping the Linear-specific names and defaults at the compatibility boundary.
